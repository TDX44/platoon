# A0 — Postgres lift-and-shift

**Date:** 2026-09-14
**Status:** ready for implementation planning
**Context:** [multi-tenant roadmap](2026-09-14-multi-tenant-roadmap.md)

## Goal

Move the application from SQLite to PostgreSQL with **no change in behaviour and
no change in schema shape**. The existing ten tests pass unmodified in intent.
Nothing a user can see changes.

This exists so that A1 (unit tree + RLS) starts from a database that supports
RLS, and so that when A1 breaks something the cause is unambiguous.

## Non-goals

- No unit tree, no `units` table, no access changes. `platoon TEXT` stays exactly
  as it is.
- No RLS policies. RLS keys on `root_id`, which does not exist until A1. A0
  prepares the *connection plumbing* RLS needs; the policies come later.
- No timestamp type change. See "Timestamps stay TEXT" below.
- No new features.

## Deployment

Postgres runs as a compose service beside the app on prodsrv02, `postgres:17`,
data on a named volume. The box has 51G free.

A managed instance would also work and is a one-line change to `DATABASE_URL`
later; a container is chosen because the backup story here is already local and
well established (`scripts/backup-db.sh`, three copies, nightly), and keeping the
database in the same compose project keeps the deploy a single
`docker compose up -d --build`.

The app connects as a **non-owner role**. Schema objects are owned by a migration
role; the application role gets `SELECT/INSERT/UPDATE/DELETE` only. This is set
up in A0 even though RLS arrives in A1, because retrofitting ownership after
policies exist is how the "policies silently do nothing" failure happens.

## Driver and connection lifecycle

`psycopg` 3 with `psycopg_pool`. Gunicorn runs `-w 2`, so a small pool per
worker.

`get_db()`'s current contract — a fresh connection per call, closed by the caller
— has to change. RLS reads a session variable, so a connection must know who is
asking, which means one connection per *request*:

- `before_request` checks out a connection from the pool and puts it on `g`.
- `teardown_request` commits or rolls back and returns it.
- `get_db()` returns `g`'s connection instead of opening one.

Code outside a request context (`init_db()` at import, the midnight reset
thread, the tests) gets an explicit connection rather than `g`.

### `log_action` joins the caller's transaction

`log_action` currently opens its own connection and carries a comment warning
that calling it while holding a write transaction self-deadlocks. That hazard
exists *only* because SQLite has a single writer. In Postgres it becomes a bug
to keep it: an audit row written on a separate connection can commit for a change
that then fails.

`log_action` uses `g`'s connection and commits with the change it describes. The
warning comment is deleted along with the behaviour it described.

## Mechanical conversion

Inventory taken from the current `server.py`:

| Thing | Count | Becomes |
|---|---|---|
| `?` placeholders | 156 `execute` sites | `%s` |
| `sqlite3.Row` | 1 | `psycopg.rows.dict_row` — `row['x']` keeps working |
| positional row reads | 3 | named keys |
| `cur.lastrowid` | 6 | `INSERT ... RETURNING id` |
| `INSERT OR IGNORE` / `OR REPLACE` | 10 | `ON CONFLICT DO NOTHING` / `DO UPDATE` |
| `AUTOINCREMENT` | 6 | `GENERATED BY DEFAULT AS IDENTITY` |
| `DEFAULT (datetime('now','localtime'))` | 4 | see below |
| `PRAGMA foreign_keys = ON` | 1 | delete — Postgres always enforces |

`CREATE TABLE IF NOT EXISTS` works in Postgres, so `init_db()` keeps its shape
and its role as the only migration mechanism.

### Timestamps stay TEXT

Stored timestamps are `'%Y-%m-%d %H:%M:%S'` strings written by `app_stamp()`,
and the four column `DEFAULT`s that use `datetime('now','localtime')` exist only
as a fallback for rows written outside that path.

They stay TEXT. Converting to `timestamptz` reopens the duty-day problem that
`app_now()` / `app_stamp()` / the `org_timezone` setting already solve and that
`tests/test_timezone.py` guards. A mechanical port is the wrong moment to
re-litigate a solved question.

The four defaults become `to_char(now(), 'YYYY-MM-DD HH24:MI:SS')` so they
produce the identical string shape. Revisiting this is a candidate for a later
project, not a blocker.

## Data migration

A one-time script, `scripts/sqlite-to-pg.py`:

1. Read every table from the SQLite file.
2. Insert into Postgres in foreign-key order.
3. Reset identity sequences to `MAX(id)`.
4. Verify row counts per table and abort loudly on mismatch.

Run against a copy first (see Rehearsal). Production runs it once at cutover
with the app stopped.

## Backups

`scripts/backup-db.sh` currently takes an integrity-checked SQLite snapshot,
keeps 30 days, rsyncs to prodsrv04, and records the outcome in
`backups/LAST_BACKUP`. Left alone it would keep backing up a stale SQLite file
to three locations and **reporting success**.

It converts to `pg_dump` in the same change, keeping the 30-day retention, the
prodsrv04 rsync and the `LAST_BACKUP` record. `scripts/backup-copy.sh` (the
Google Drive third copy) follows the file it is given and needs no logic change.

## Tests

Each test currently sets `DATA_DIR` to a fresh temp directory and imports
`server`, getting a private SQLite file. The Postgres equivalent keeps that
isolation with a **schema per test**: the harness creates `test_<random>`, sets
`search_path`, runs `init_db()`, and drops the schema at the end.

- A shared helper, `tests/dbharness.py`, owns create/teardown so the ten tests
  each change by about three lines.
- CI gains a `postgres:17` service container and `DATABASE_URL`.
- Locally a developer needs Postgres running. The dev stack's container serves;
  `DATABASE_URL` points at it.
- `tests/test_mobile_layout.py` keeps its existing skip-if-no-Playwright
  behaviour, unchanged.
- One new test, `tests/test_pg_port.py`, asserts the things the conversion table
  above can silently get wrong: that an insert returns a usable id, that
  `ON CONFLICT` is idempotent, that identity sequences survive the migration,
  and that an audit row and the change it describes commit together.

## Rehearsal and cutover

Rehearsal on `platoondev.carr7.com`, against a copy of production's database:

1. `cp` production's `accountability.db` into dev's data directory.
2. `docker compose up -d --build` in the dev checkout.
3. Run `scripts/sqlite-to-pg.py`, watch it against 160KB of real rows.
4. Exercise the app; run the suite.
5. Fix, restore the pristine copy, repeat.

Cutover on production:

1. Manual `scripts/backup-db.sh` — not just the 03:10 timer's copy.
2. Stop the app. Keep the SQLite file in place, untouched.
3. Start Postgres, run the migration script, verify row counts.
4. Start the app on the new image.
5. Verify the roster, one absence edit, and one audit entry.

**Rollback** is redeploying the previous image, which still reads the SQLite file
left in place. That is the reason step 2 does not delete it. The file stays until
a week of clean Postgres operation has passed.

Unlike A1, this migration is reversible — which is most of the argument for
shipping it on its own.

## Risks

- **Silent RLS bypass later.** Mitigated in A0 by establishing non-owner
  ownership now rather than retrofitting it in A1.
- **A missed `?` placeholder.** psycopg raises rather than guessing, so these
  surface as errors, not as wrong data. The 156 sites are found by grep, not by
  memory.
- **`lastrowid` returning `None` silently.** Six sites; `test_pg_port.py` covers
  the pattern.
- **Backup script left on SQLite.** Called out above because its failure mode is
  reporting success.
